## Предварительная числовая рубрика (пилот 22.10)

LLM теперь обязана возвращать `scorecard` по 5 официальным качественным группам критериев (числовые уровни 0–3 — гипотеза команды). Общий балл вычисляется сервером после проверки evidence, а не доверяется модели. При 3+ оценённых группах, включая мотивацию и нагрузку: `score` целый 0–3, `score_status=pilot_unvalidated`, `score_raw` и пять rationale в `scorecard`; при недостатке сведений — `score=null` и `insufficient_evidence`. Новые ответы без scorecard не проходят строгую live-валидацию. Старые сырые ответы можно валидировать отдельно только с явным `allow_legacy`. Детали: [рубрика и ограничения](20-gim-scoring-pilot-20261022.md). Это не доказанное совпадение с историческими баллами ГИМ; примеры требуют проверки куратором.

## Бюджет вопросов и неподтверждённые часы (исправление 21.10)

LLM-интервью: системный промпт просит выбрать 1–2 приоритетных вопроса, сервер после строгой проверки ответа сохраняет не более двух разных вопросов, сохраняя их порядок. Это ограничение нашего UX, не числовая норма музея. Для формы сервер возвращает максимум три уточнения, предпочитая возраст и реальный график. Уже известные ответы не надо запрашивать повторно.

Утверждение о часах фондов «10–18 по будням» удалено из промпта: его нет в исходном кейсе. Расписание проверяется у координатора. Утверждение о минимуме 8–12 ч/месяц удалено из объяснения дополнительных вопросов; 8 часов — не подтверждённый обязательный минимум.

## Настройки

- `GIM_EVALUATION_MODE=demo` или `llm` (по умолчанию demo).
- `GIM_LLM_ENDPOINT` — полный URL совместимого `/v1/chat/completions`.
- `GIM_LLM_MODEL` — имя модели, загруженной сервером.
- `GIM_LLM_API_KEY` — необязательный Bearer, **не коммитить ключ**.
- `GIM_LLM_TIMEOUT` — секунды: универсальный адаптер без env — 30; launcher ReformBoss задаёт 300 по умолчанию (`-TimeoutSeconds`, диапазон 1–300). Пробник читает ту же переменную, `--timeout` имеет приоритет.
- `GIM_LLM_JSON_MODE=1` — попросить ответ в формате JSON.
- `GIM_LLM_STREAM=1` — собирать потоковый ответ OpenAI-compatible API; launcher ReformBoss включает это автоматически.
- `GIM_LLM_MAX_TOKENS=4096` — ограничение ответа в launcher ReformBoss.
- `GIM_LLM_FALLBACK_TO_DEMO=1` — явный резерв при ошибке модели; без него ошибку показываем как HTTP 503.

Текущий командный провайдер — ReformBoss, модель `deepseek-v4.1-flash`. Отдельный unit live-тест пропускается без явного GIM_RUN_LIVE_TEST=1 и окружения провайдера; он не отражает состояние отдельно запущенного сервера.

## Выход

JSON со следующими полями: `score` (0–3 либо `null` при недостатке данных), `score_status` (`pilot_unvalidated` либо `insufficient_evidence`), `evaluation_mode` (llm/rules_demo), `summary`, `strengths`, `possible_problems`, `recommended_direction`, `recommended_direction_label`, `direction_reason`, `fit_for_museum`, `fit_for_candidate`, `interview_questions`, `scorecard` и `evidence`. Вызовы LLM проверяются по схеме Pydantic и дословным цитатам из переданных ответов. Текстовые ошибки провайдера не возвращаются пользователю в необработанном виде.

### Продуктовое правило ГИМ по нагрузке

**Первый курс бакалавриата, полная ставка и несколько параллельных волонтёрских проектов — отрицательные предварительные сигналы** по регулярности и риску недолгого участия. Логика `backend/availability_policy.py` добавляет их в `possible_problems` и `fit_for_museum` даже когда LLM недостаточно явно их выделила.

При конкретных стабильных свободных часах/днях возможно **индивидуальное исключение**. Никаких жёстких автоматических отказов по статусу; решение остаётся за куратором. Шкала 0–3 остаётся пилотной и не откалибрована на исторической выборке.

## ReformBoss — запуск живой модели без записи API-ключа

Этот вариант предназначен для команды ГИМ и использует предоставленный участником OpenAI-compatible API:

- **Base URL**: `https://api.reformboss.com/v1`
- **Полный endpoint**: `https://api.reformboss.com/v1/chat/completions`
- **Первый кандидат**: `deepseek-v4.1-flash` (проверенный ID из авторизованного GET /v1/models в ReformBoss; вариант `deepseek-v4.1-flash-1017` также есть в каталоге, но launcher закрепляет основной ID).
- Для сравнения: `deepseek-v4-flash`, `deepseek-v4-pro`.

В PowerShell из корня клонированного репозитория:

```powershell
python -m pip install -r requirements.txt
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\launchers\start-reformboss.ps1
```

Скрипт читает `GIM_LLM_API_KEY` из окружения или локального `.env`. Если ключа там нет, скрипт спросит его обычным видимым вводом. Затем выполнит один настоящий API-запрос с вымышленной анкетой, проверит JSON-контракт и запустит FastAPI на свободном локальном порту начиная с `8765`. `.env` исключён из Git. Остановка: Ctrl+C.

Выбрать другую модель (одна проверка):
```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\launchers\start-reformboss.ps1 -Model deepseek-v4-pro
```

Сравнить **три модели** (три реальных вызова, расходуют лимит API; после проверки приложение запускается на выбранной модели):
```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\launchers\start-reformboss.ps1 -Compare
```

Если шлюз не принимает `response_format: json_object`, повторите с `-DisableJsonMode`; проверка JSON остаётся включённой в приложении. Проверка без дополнительного вызова при запуске: `-SkipProbe`.

**Не путать лимит сообщений Telegram-бота и лимит ReformBoss API.** Узнайте ограничения непосредственно в сервисе. Используйте только вымышленные анкеты до подтверждения условий обработки данных. Если live-проверка не прошла, скрипт не запускает приложение в режиме LLM и не выдаёт `rules_demo` за настоящий ИИ.

## Граница данных: актуальный аудит

Текущий evaluate() исключает applicant_name и application_id, но остальные поля ApplicationInput, включая email/vk_url/birth_date, передаются в answers. Выделенного allowlist в main пока нет (#28). Все зафиксированные live-проверки использовали synthetic input. При переносе полезного allowlist из scoring.py Саши сохранить контракт текущих recommendations и evidence.

В fe348a5 rag_llm Саши уже использует настраиваемый chat endpoint, а Neo4j допускает full-text fallback без OpenAI embedding key; прежний блокер конфигурации снят. Совместный PostgreSQL + Neo4j + модель этим аудитом не подтверждён. Четыре provider_network_error относятся к старому сравнению fe348a5; на ef311e8 появились Qwen-прогоны с результатами ниже. Для принятия нужны live-проверка, общий deadline и согласованная рубрика/решение pilot-v1 (#32); таймаут и результаты main нельзя автоматически переносить на другой путь.

## Вопросы и ограничения промпта

В main вопросы внутри формы формирует Python, а DeepSeek после отправки возвращает вопросы для собеседования. Схема допускает 1–12 вопросов, поэтому 11 не нарушают наш контракт, но такой объём не требуется музеем. Нужен отдельный фикс приоритизации, повторов и небольшого бюджета вопросов. Категоричное расписание фондов 10–18 в промпте взято из рабочей XLSX команды и пока не подтверждено первоисточниками. Эти ограничения зафиксированы, поведение кода данной поставкой не изменено.

На `sanya_gpt_analysis@ef311e8` сохранены новые сравнения Qwen: часть JSON валидна, часть падает с invalid_candidate_analysis. Прежние четыре provider_network_error относятся к снимку fe348a5. [Точная сводка](18-criteria-source-audit-20261021.md) не подтверждает качество RAG или его интеграцию в main.
