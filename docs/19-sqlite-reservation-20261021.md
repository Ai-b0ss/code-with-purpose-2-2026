# ГИМ: резервирование ID до вызова оценщика

## Почему потребовалось

Старый обработчик сначала выполнял SELECT, потом медленный LLM и только потом INSERT.
Два одновременных POST с одинаковым application_id успевали оба вызвать LLM, а
один из INSERT мог завершиться sqlite3.IntegrityError (HTTP 500).

## Новая последовательность

1. Под короткой транзакцией SQLite BEGIN IMMEDIATE проверяем существующую анкету.
2. Для нового ID атомарно создаём запись application_reservations с уникальным
   токеном и временем. Никакую транзакцию не держим открытой во время работы модели.
3. Конкурирующий POST с тем же ID ждёт окончательной записи, после чего получает
   сохранённый результат с created=false без дополнительного вызова оценщика.
4. Первый POST с верным токеном одной транзакцией INSERT-ит анкету и удаляет
   резерв. При ошибке оценщика резерв удаляется, приложение не создаёт пустую анкету.
5. Если другой процесс/поток удерживает ID дольше допустимого времени,
   второй HTTP-запрос получает 409 и Retry-After: 3. Клиент может повторить POST
   с тем же ID. По истечении 10 минут резерва после аварии допускается перехват;
   старый токен больше не может записать результат.

## Границы

- SQLite гарантирует единственность строки applications(id) и координирует процессы
  через одну файловую БД. Не переносить разные экземпляры на разные SQLite-файлы.
- Exactly-once LLM-вызов через смерть процесса гарантировать нельзя без
  idempotency key на стороне провайдера. После аварии спустя 10 минут возможен новый
  вызов модели — это явная граница гарантии.
- Ожидание для второго POST — от 30 до 360 секунд (таймаут модели + 30 с,
  по умолчанию 210 с). Длительный расчёт может вернуть 409, не выдавая 500.
- Не изменены контракты успешной отправки, экспорт, исходные оценки и
  правила согласия на обработку данных.
- Новая таблица application_reservations создаётся при первом подключении.

## Проверки

На изолированной Windows-копии проекта:
- pytest: 54 PASS, 1 live SKIP, 54 subtests;
- локальный smoke с настоящим Uvicorn/SQLite: 73 PASS, 1 SKIP, 0 FAIL;
- новый регрессионный набор: два одновременных POST с одинаковым ID ->
  один вызов оценщика, одна строка, created=true/false; ошибка модели ->
  резерв очищается; старый резерв после аварии -> восстанавливается.
- Не выполнялись нагрузочные испытания нескольких серверных процессов,
  длительная настоящая DeepSeek-оценка или сценарий отключения питания.
  Перед публичным запуском также нужен доступ к API персональных данных (#28).
