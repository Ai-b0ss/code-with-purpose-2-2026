## 1. Зачем продукт

Волонтёрская программа музея закрытого типа: мест порядка 100, желающих больше. Координаторы читают анкеты и приглашают подходящих кандидатов на очные интервью; трудозатраты высоки. Продукт должен помогать **обеим сторонам**: оценивать, подходит ли кандидат конкретной программе, и объяснять кандидату, подходит ли музейная программа его ожиданиям.

## 2. Фактические требования заказчика (из описания кейса)

- Диалоговая анкета с вопросами и ответами.
- Нейросеть формирует короткие контекстные уточнения прямо во время заполнения.
- Нейросеть готовит вопросы для очного собеседования с координатором.
- Результат для координатора: анкета и объяснимая оценка соответствия.
- Проверка объективных требований, например 18+.
- Удобная аналитика по кандидату и по всей группе, желательно дашборд/графики с переходом в детали.
- Экспорт результатов по кандидату в табличном формате.
- Простота использования, минимум необходимости в поддержке.
- **Любая платформа, кроме Telegram.** VK — текущий канал общения музея, но его API не является обязательным в формулировке исходного задания.

## 3. Анкета и данные (из файла с вопросами)

Обязательные блоки: согласие на обработку персональных данных; ФИО/контакты/страница VK/дата рождения; статус, образование; интересы/опыт/языки; мотивация и ожидания; месячная доступность; хобби; интересующий тип участия; источник информации о программе.

Направления: организационное, проектное, фондовое, инклюзивное, медиа; предусмотрено «ещё не определился».

### Группы исходных критериев для оценки сотрудниками музея
1. Мотивация и осознанность выбора.
2. Опыт и навыки.
3. Курс обучения и нагрузка.
4. Цифровой след и полнота анкеты.
5. Логистика и бытовые вопросы.

**Замечание по качеству и справедливости:** в исходных критериях встречаются косвенные признаки (курс, закрытость страницы VK, наличие опыта/город). Не вводить автоматический отказ/штраф только за них без явного, проверяемого, согласованного основания. Возрастную проверку 18+ выполнять детерминированно; остальные оценки — объяснимая рекомендация человеку. Не читать внешние профили VK без согласия и отдельного запроса.

### Примеры уточняющих тем
- Фонд: какие фонды интересны и готовы ли рассматривать альтернативные направления.
- Проекты: ближе мастер-классы, квесты, экскурсии или игры.
- Организация: предпочтительные группы посетителей.
- Медиа: фото, видео, тексты, дизайн, контент-планы.
- График: регулярный или гибкий, другие волонтёрские обязательства.
- Мотивация: ожидания и конкретные идеи для музея.

## 4. Минимальный вертикальный сценарий (P0)

1. **Кандидат** открывает веб-приложение (не Telegram); видит вводную о программе, согласие и основные вопросы. Для демонстрации используем синтетическую личность.
2. **Программа** проверяет обязательные поля и отдельно объективные условия (18+), предлагает 1–3 уместных уточнения без повторов и выдуманных фактов.
3. **Оценщик** формирует строго валидируемый JSON: категории, обоснование из ответов, сильные стороны, риски/нехватка данных, уровень определённости, альтернативные направления. Результат — рекомендация, не автоматическое решение о приёме.
4. **Координатор** видит список заявок, карточку кандидата, основания оценки и список вопросов для интервью. Может скорректировать или подтвердить оценку.
5. **Экспорт:** CSV/XLSX с псевдонимными идентификаторами, выбранными критериями и заключением. Поля с персональными данными по умолчанию исключить из демо-выгрузки.

## 5. Что отдельно проверить до реализации

- Политика обработки персональных данных: согласие, хранение, доступ, удаление. Нельзя отправлять ФИО, даты рождения, почту и VK-ссылки в необязательные внешние LLM.
- Разрешён ли локальный веб-интерфейс как финальное решение (исходный документ говорит «любая платформа, кроме Telegram»); нужна ли публикация публичной ссылки.
- Формула оценивания по критериям, веса и значение исторических баллов (0–3 на слайде). Чего именно эти баллы касались?
- Предоставляются ли обезличенные примеры с человеческими оценками? Нельзя считать прошлую активность единственным доказательством качества кандидата.
- Ожидается ли реальный VK-бот или достаточно веб-прототипа; если потребуется интеграция — доступ к тестовому сообществу.
- Ограничения на использование внешней модели, сроки сдачи и формат презентации.

## 6. Рекомендуемая архитектура (предложение, не требование заказчика)

Один backend, SQLite для прототипа, простой web UI и разделённые модули `questions`, `rubric`, `evaluator`, `storage`, `export`. Режим **offline/sample** на вымышленных ответах обязателен: не зависеть на защите от внешнего API. AI-модель подключать через интерфейс, проверять JSON-схему, ошибки и повторения, а для важных выводов сохранять цитаты-основания из ответа (без PII). Без сложных микросервисов.

## 8. Приоритеты

**P0:** одна работающая анкета, корректные уточнения, валидируемая оценка, карточка координатора, CSV и offline-демо.

**P1:** фильтры списка, визуальная аналитика всей выборки, модельная проверка против независимой ручной разметки, VK-интеграция (только если потребуется).

**P2:** личный кабинет с авторизацией, продвинутая статистика, интеграции с CRM, развёртывание промышленной системы.

Рекомендуемый порядок: первый работающий локальный маршрут → API контракт → отдельные UI/backend/оценщик → тесты → сквозная сборка → заморозка → защита.
